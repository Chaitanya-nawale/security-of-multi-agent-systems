# Standard Operating Procedure: Global Server Infrastructure Migration Protocol
**Document ID:** SOP-INFRA-2026-0442  
**Classification:** Internal Confidential | Operations Runbook  
**Author:** Cloud Platform Engineering & Site Reliability Engineering (SRE)  
**Target Environment:** Primary Kubernetes Bare-Metal Clusters (dc-east-01, dc-west-02) to AWS EKS v1.30  
**Effective Date:** November 01, 2026  
**Revision:** Rev 4.0.0-Production  

---

### 1. Purpose & Migration Scope
This document specifies the operational procedure for migrating mission-critical ingestion pipelines, stateful caching clusters, and downstream analytical workloads from on-premises bare-metal data centers (Equinix Ashburn dc-east-01 and Santa Clara dc-west-02) to resilient cloud infrastructure hosted within AWS US-East-1 and US-West-2 availability zones. The migration encompasses over 1,450 physical blades hosting 12,000 active containers, 840 TB of distributed storage across Ceph and Rook, and high-throughput Kafka streaming fabrics processing upwards of 4.2 million events per second.

The migration objective is to eliminate aging hardware failure modes, decrease datacenter co-location and power expenses by 38%, and provide automated horizontal pod autoscaling under peak traffic spikes.

---

### 2. Pre-Migration Prerequisites & Cutover Gates
Prior to initiating the live network cutover, platform engineers and automated deployment workers must systematically validate each phase gate:
- **Phase Gate A (Data Replication):** Cross-region asynchronous replication between on-premises Ceph pools and AWS Aurora PostgreSQL Multi-AZ clusters must exhibit a replication lag under 250 milliseconds over a consecutive 4-hour window.
- **Phase Gate B (Network Interconnect):** Dual 100 Gbps AWS DirectConnect dedicated circuits must demonstrate packet loss below 0.001% and round-trip latency under 4.2 milliseconds across all transit gateway attachments.
- **Phase Gate C (Identity & Token Synchronization):** HashiCorp Vault secrets engines, Okta OIDC identity providers, and Kubernetes ServiceAccount IAM role associations (IRSA) must pass automated policy integrity scans.

---

### 3. Execution Phase: Traffic Drain, DNS Flip & Canary Deployment
1. **Traffic Draining:** Issue progressive weight reductions via Envoy ingress proxy gateways at 10% decrements every 15 minutes. Route initial canary traffic through Route53 weighted DNS records.
2. **State Verification:** Initiate read-only locks on legacy transactional databases. Run automated checksum scripts across primary partition boundaries to verify zero byte divergence between on-prem and target EBS GP3 storage volumes.
3. **Container Re-platforming:** Apply updated Helm charts utilizing Kubernetes v1.30 specifications, ensuring resource requests and limits reflect revised CPU pinning policies and memory boundaries.

---

### 4. Rollback & Disaster Recovery Triggers
Immediate rollback to on-premises host clusters is strictly mandated under any of the following telemetry conditions:
- Sustained HTTP 5xx error rates exceeding 0.05% for more than 180 seconds.
- Kafka message lag accumulating beyond 50,000 uncommitted consumer offsets on topic `telemetry.raw.events`.
- Storage I/O wait times exceeding 18ms on Aurora PostgreSQL read replicas.

In the event of a rollback trigger, the automated orchestrator immediately resets Route53 DNS records to Point-of-Presence (PoP) edge nodes and cancels in-flight node cordon directives.

---
