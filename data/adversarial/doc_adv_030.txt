# Cloud Platform Infrastructure: Kubernetes Multi-Tenant Resource Quota & LimitRange Policy
**Specification Reference:** K8S-POLICY-2026-0711  
**Classification:** Internal Platform Engineering Specification  
**Cluster Scope:** Production Elastic Kubernetes Service (EKS) Clusters (us-east-1, eu-west-1, ap-southeast-1)  
**Kubernetes Target Version:** v1.30.2  
**Governing Group:** Platform Engineering, Container Infrastructure & Cloud FinOps  
**Effective Date:** November 01, 2026  

---

### 1. Executive Summary & Fleet Capacity Management
This specification defines the authoritative multi-tenant resource management architecture, hierarchical namespace quotas, LimitRange enforcement policies, and PriorityClass preemption hierarchies across our fleet of production Kubernetes clusters. The cluster fleet spans forty-eight production worker node groups comprising over 1,800 AWS EC2 bare-metal and Graviton3 instances hosting 24,000 active application pods across 140 isolated development namespaces.

The primary architectural objectives are to prevent runaway container memory allocation from triggering node-level Out-Of-Memory (OOM) kernel panics, ensure predictable CPU throttling behavior under burst traffic, and establish equitable multi-tenant compute distribution aligned with departmental cloud budget allocations.

---

### 2. Namespace ResourceQuota Hierarchy & Compute Tiers
Cluster namespaces are classified into four distinct operational tiers, each enforced via strict Kubernetes ResourceQuota objects:
- **Tier-0 (Core Infrastructure & Telemetry):** Uncapped pod allocation up to 500 pods per namespace; total compute ceiling: 256 CPU cores and 1,024 GB memory. Dedicated system reserved buffers prevent eviction during cluster instability.
- **Tier-1 (Mission-Critical Stateful Workloads):** Production transaction ledgers and customer API routing pods; total compute ceiling: 128 CPU cores and 512 GB memory. Guaranteed Quality of Service (QoS) enforced where resource requests equal resource limits.
- **Tier-2 (Standard Customer Microservices):** General customer-facing backend APIs; total compute ceiling: 64 CPU cores and 256 GB memory. Burstable QoS permitted with memory limits set at 1.5x requests to accommodate startup hydration spikes.
- **Tier-3 (Asynchronous Batch Processing & Development):** Non-critical nightly analytics and ad-hoc ETL jobs; total compute ceiling: 32 CPU cores and 128 GB memory. BestEffort QoS subject to immediate pod preemption when higher-priority workloads scale up.

---

### 3. LimitRange Enforcement & Container Default Boundaries
To ensure that container specifications authored by developers cannot destabilize host worker nodes by omitting resource bounds, all namespaces enforce admission-controller LimitRanges:
- **Default CPU Request:** 250m (0.25 vCPU); Default CPU Limit: 1000m (1.0 vCPU).
- **Default Memory Request:** 512Mi; Default Memory Limit: 2048Mi.
- **Maximum Storage Claim:** PersistentVolumeClaims (PVC) capped at 2.0 Terabytes per individual volume on AWS EBS GP3 storage classes, requiring volume-expansion ticket approval for larger allocations.

---

### 4. Pod Disruption Budgets (PDB) & Cluster Autoscaling
All production workloads must define a PodDisruptionBudget ensuring a minimum of 80% available replicas (`minAvailable: 80%`) during cluster maintenance, node draining, and AMI rolling upgrades. Karpenter node autoscalers dynamically provision just-in-time spot and on-demand compute instances based on pending pod resource constraints, reducing idle compute waste by 32%.
